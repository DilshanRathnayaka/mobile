Review of the money-management app — 11 October 2026

Owner clarification after this review: the deployed app uses Flutter mobile + Supabase only, with Google Authenticator intended for 2FA. The separate Node server finding is not applicable to that deployed architecture. See `ANTIGRAVITY_IMPLEMENTATION_PLAN.md` for the implementation handoff scoped to Flutter and Supabase.

The current implementation focuses on crypto holdings, transactions, salary allocations, and portfolio reports. Before using it as the sole record of personal finances, fix authentication, currency handling, and accounting consistency. Daily expenses, cash accounts, liabilities, and other investment classes still need a unified ledger.

Scope: Flutter source, Android/iOS configuration, the sibling `../supabase_schema.sql`, and the sibling `../server` source. The active Flutter providers use Supabase directly; `ApiService` and the Firebase/MongoDB server are a separate, currently unreferenced path in the mobile source reviewed. Server vulnerabilities below are conditional on deploying that server. The deployed Supabase configuration, applied migrations, backups, and live RLS behavior were not inspected. No real accounts or financial records were modified, and no production endpoints were probed. Source files were changing during the review; analyzer results below reflect the final run during this review.

Priority convention: P1 = fix before relying on real financial records; P2 = correctness, hardening, or release work to complete next.

1. **P1 — The displayed 2FA protection does not verify a second factor.** `lib/screens/auth/auth_screen.dart:105` accepts any six-character input. Enrollment in `lib/screens/profile_screen.dart:504` checks only length as well. `lib/providers/security_provider.dart:55` uses the same hardcoded sample authenticator secret, while settings are local preferences. There are no MFA enrollment/challenge/verification calls, and the supplied RLS policies do not enforce MFA assurance. A person who has the password can pass the apparent second-factor screen without the authenticator. Replace this with Supabase MFA enrollment, challenge, verification, and applicable `aal2` authorization policies. Require recent authentication for disabling MFA and provide a recovery flow. Remove “2FA Protected” until protection is implemented. [Supabase MFA documentation](https://supabase.com/docs/guides/auth/auth-mfa).

2. **P1 — App unlock can be skipped or report success without authentication.** `lib/providers/security_provider.dart:113` returns true when the device lacks support; the `PlatformException` handler also returns true. `lib/main.dart:43` sends a persisted user straight into the main screen without an app-lock challenge. There is no app-resume lock handler. The biometric button navigates without establishing or verifying an account session (`lib/screens/auth/auth_screen.dart:122`). This is a local UI/authentication defect; it does not itself bypass Supabase RLS for an unauthenticated request. Fail closed, require a valid account session, and implement an independent device-unlock gate on launch/resume. Android uses `FlutterActivity` in `android/app/src/main/kotlin/com/assetmanager/app/mobile/MainActivity.kt:5`, whereas the plugin requires `FlutterFragmentActivity`. The iOS plist has no Face ID usage description. The biometric permission is already contributed by the Android dependency, so its absence from the app manifest alone is not a defect. [Android plugin setup](https://pub.dev/packages/local_auth_android).

3. **P1 — Signing out does not clear account-specific provider data.** `lib/screens/profile_screen.dart:387` signs out and navigates, but the root `ProviderScope` remains alive. Transaction and salary providers in `lib/providers/portfolio_provider.dart:37` and `:89` are neither account-keyed nor invalidated. Login refreshes only the portfolio summary (`lib/screens/auth/auth_screen.dart:31`). On the same running app, user B can therefore be shown user A's cached salary/transaction data until refreshed. Scope all private providers to the authenticated user, clear them on every account transition, and prevent old in-flight requests from repopulating the new session. Listen to auth-state changes, including expiry/sign-out.

4. **P1 — LKR salary entries are saved as if they were USD.** The salary dialog labels fields with the selected currency (`lib/screens/salary_dca_screen.dart:277`), then passes their raw numeric values to storage (`:314`). `lib/core/utils/formatters.dart:9` treats every stored amount as USD and converts again for display. Example: choosing LKR and recording an allocation of Rs 10,000 causes the history to display Rs 3,050,000 with the configured 305 multiplier. Store original amount, original currency, the rate used, rate date/source, and normalized base amount. Convert exactly once at the input boundary. `lib/providers/currency_provider.dart:20` also fixes USD/LKR at 305 with no date or rate refresh; this is a hardcoded application value, not a verified current exchange rate.

5. **P1 — Saving/editing salary allocations duplicates deposits and permits partial saves.** `lib/data/services/supabase_service.dart:301` upserts one allocation per month, then unconditionally inserts a fresh `SALARY_DEPOSIT` at `:311`. Editing an allocation adds another deposit; deleting it at `:327` leaves deposits behind. The writes are separate, so a second-write failure leaves the first committed. The dialog ignores the boolean result and closes even on failure (`lib/screens/salary_dca_screen.dart:314`). Use one transactional database operation, link each deposit to its allocation, enforce uniqueness/idempotency, and update/delete consistently. Disable repeated submission and keep failed edits visible. Reconcile already duplicated data before treating historical totals as authoritative. Salary changes should refresh transaction reports too.

6. **P1 — Fully sold positions lose their realized profit in the summary.** `lib/data/services/supabase_service.dart:59` selects only holdings with positive quantity, then sums realized P&L from that subset. Buying one unit at $100 and selling it at $120 should retain $20 realized profit; once the quantity is zero this position is omitted. If no open positions remain, the entire summary becomes empty. Aggregate realized P&L independently from the open-position query. The sibling server has the same issue in `../server/src/controllers/portfolioController.js:6`.

7. **P1 — Moving a transaction to another coin leaves its former holding stale.** The editor permits changing the asset; `lib/data/services/supabase_service.dart:213` updates `coin_id`. The SQL trigger chooses `COALESCE(NEW.coin_id, OLD.coin_id)` (`../supabase_schema.sql:137`) and recalculates only that coin. Editing a BTC transaction into ETH recalculates ETH but leaves the old BTC quantity/cost. Rebuild both the old and new asset when their identities differ, inside the same transaction. Include asset changes, transaction-type changes, backdating, and deletion in accounting tests.

8. **P1 — New Binance selections use an incompatible asset identifier.** `lib/screens/add_transaction_screen.dart:63` and its coin-selection callback store `coin.symbol.toLowerCase()` as the coin ID, e.g. `btc`. The valuation service sends that ID to the CoinGecko `/simple/price?ids=...` endpoint, whose own existing code path uses IDs such as `bitcoin` (`lib/data/services/supabase_service.dart:346`). This can split one asset into multiple holdings (`btc` versus `bitcoin`) and fail to retrieve its intended market price. Use a canonical internal asset ID with explicit provider-specific mappings; symbol alone is insufficient, especially across chains. Distinguish USDT quote amounts from USD as well.

9. **P1 — Invalid trades can manufacture accounting results.** Input validation checks whether text parses, without consistently checking positivity, finiteness, or available quantity. In `../supabase_schema.sql:25`, price, fee, and total lack the needed numeric/business constraints; client-supplied totals are trusted. The sell calculation at `:159` clamps negative holdings to zero instead of rejecting an oversell. A sell with no prior inventory can record profit on a zero cost basis. Validate transactions in the database, derive totals from canonical values, and reject inventory violations throughout the chronological history, including edits/deletes of earlier buys. Serialize concurrent changes to the same holding so two requests cannot independently consume the same inventory. Preserve an explicit short-selling model only if that product behavior is intentionally supported.

10. **P1 — Reports display invented historical points and conceal missing prices.** `lib/screens/analytics_screen.dart:280` creates the equity curve from fixed multipliers (0.92, 0.96, etc.) rather than valuation history; range selection changes the label without fetching period history. `lib/data/services/binance_service.dart:48` returns hardcoded market tickers on a network failure. `lib/data/services/supabase_service.dart:82` substitutes average purchase price for missing market prices, making unrealized P&L appear zero. Replace these with dated valuation snapshots, explicit quote timestamps, a known last-good quote marked stale, or an unavailable state. Never label demonstration values as live financial data. Deposit-driven account growth must be distinguished from investment return.

11. **P1 if deployed — The separate Node server accepts unverified identities when Firebase initialization is unavailable.** `../server/src/middleware/authMiddleware.js:44` interprets the Bearer token itself as a UID. Despite the comment, there is no production environment guard. Missing or invalid service-account configuration therefore weakens authentication instead of preventing startup. A controlled in-memory check using the actual middleware confirmed this with `NODE_ENV=production` and a mock database. Fail startup when required authentication configuration is unavailable, verify real tokens, and never fall back to a caller-selected identity. This is not the auth path currently used by `supabaseServiceProvider`.

12. **P2 — API failures appear as valid empty financial accounts.** `lib/data/services/supabase_service.dart:135`, `:169`, and `:287` catch read errors and return empty models/lists. The providers then expose successful empty data, so UI error/retry branches do not run. Propagate typed errors; distinguish “no transactions” from “could not load transactions,” retaining a clearly dated last-known result if appropriate. Update/delete also return success without checking an affected record, so stale IDs may produce misleading success notices.

13. **P2 — Financial precision needs explicit rules.** Dart calculations use binary doubles; schema monetary values and average price are restricted to four decimal places (`../supabase_schema.sql:33`, `:55`). A token price of 0.00001045 can round to zero in that schema. `Formatters.cryptoAmount` rounds all quantities to four decimals, hiding small balances. Use decimal or fixed-point representations with sufficient asset-specific precision, exact serialized decimal input, documented rounding, and full-detail views. Keep fiat cents where relevant. Label the remaining cost basis separately from lifetime capital contributed: the current “Cumulative Capital Invested” label uses remaining holdings cost.

14. **P2 — History can silently stop at the API row limit.** `lib/data/services/supabase_service.dart:150` retrieves transactions without pagination. Supabase defaults to a maximum of 1,000 rows, although a deployed project's setting can differ. Paginate history and exports, and calculate report aggregates in database queries rather than from whichever page the UI loaded. [Supabase select documentation](https://supabase.com/docs/reference/dart/select).

15. **P2 — Export is a placeholder, and recovery needs a real workflow.** `lib/screens/analytics_screen.dart:714` only closes the sheet and shows a “captured” message; it does not write/share a statement. Implement an actual CSV export first, with dates, currencies, fees, account/asset IDs, and complete pagination. Add a versioned backup/restore format and test restoring it into an empty account. Keep private backups encrypted. Add password reset, confirmation/resend handling, account deletion, and session/device management. Signup currently navigates onward without checking whether a session exists after email confirmation is requested.

16. **P2 — Device data and privacy controls need hardening.** `lib/main.dart:15` uses the SDK's default persistence; the installed Supabase Flutter 2.18.2 implementation selects `SharedPreferencesLocalStorage` and serializes the session there. Use an appropriate Keychain/Keystore-backed session storage implementation for mobile, plus an explicit backup policy. This concerns device storage access; it does not imply that other ordinary apps can freely read the sandbox. Balance hiding is applied on some screens but not salary, report, and transaction views. Make privacy mode consistent and consider obscuring app-switcher previews. Security preferences should be tied to the correct account/device instead of being global flags presented as server protection.

17. **P2 — Android release settings need completion.** `android/app/src/main/AndroidManifest.xml` has no INTERNET declaration. The existing debug merged-manifest report attributes INTERNET solely to `src/debug/AndroidManifest.xml`; the profile variant also has it, but the main/release configuration does not. Add it to the main manifest and verify the actual release artifact. `android/app/build.gradle.kts:37` signs release with the debug signing configuration. Configure a release upload key, application name/icon, and release-device checks. No release build or physical-device biometric test was performed. [Flutter networking setup](https://docs.flutter.dev/data-and-backend/networking).

The supplied SQL has a useful baseline: RLS is enabled on all four financial/profile tables, with ownership policies, foreign keys, and per-user uniqueness constraints. The configured client JWT identifies itself as `anon`, not `service_role`; an anon/publishable key in a client is not itself a secret exposure. Actual security depends on deployed grants/policies and user authentication. Verify anonymous and cross-user reads/writes with two test accounts. Derived holdings should be protected from arbitrary direct client writes (`../supabase_schema.sql:112` currently allows an owner to manage them), and security-definer functions should use a controlled search path. [Supabase API key guidance](https://supabase.com/docs/guides/getting-started/api-keys).

**Practical product work, in recommended order**

| Order | Add/change | Everyday benefit |
| --- | --- | --- |
| 1 | Accounts for bank, cash, e-wallet, exchange, and credit card; opening balance and reconciliation | Know where the money actually is and match the app to statements. |
| 2 | Income, expense, transfer, investment purchase/sale, fee, interest, dividend, refund, and adjustment entries | Represent daily finances without forcing everything into BUY/SELL/SALARY_DEPOSIT. Transfers between your own accounts must not count as new income or spending. |
| 3 | Quick expense entry, categories, notes, receipt attachment, search/date/account filters | Make daily recording fast enough to sustain. |
| 4 | Monthly category budgets, actual-vs-budget, recurring bills/subscriptions, due reminders | See spending left for the month and avoid forgotten bills. Separate planned salary allocations from money actually transferred. |
| 5 | First-class LKR and multi-currency accounts with dated conversion rates | Preserve what was paid in its original currency and explain FX gains/losses. |
| 6 | Savings, fixed deposits, shares/funds, gold/property/manual assets, loans and credit cards | Track all assets and liabilities; calculate net worth and available cash separately. Add maturity dates and interest/dividend events where relevant. |
| 7 | Emergency-fund and other savings goals with target date and progress | Make the app useful for decisions beyond market price changes. |
| 8 | Real CSV import/export, duplicate detection, backup/restore, edit history and undo/reversal | Recover records, reconcile bank/exchange statements, and correct mistakes safely. |
| 9 | Offline capture with visible pending/failed sync and idempotent retry | Record spending when disconnected without creating duplicates on reconnection. |
| 10 | Historical net worth, cash flow, fees, realized/unrealized returns, and allocation reports | Explain changes using actual transactions and prices, with deposits separated from performance. |

For the home screen, prioritize available cash, this month's income, expenses, budget remaining, upcoming bills, and total net worth. Put market tickers and hypothetical profit tools inside Investments. Use familiar navigation labels such as Overview, Transactions, Accounts, Investments, and Reports. A useful foundational flow is: salary increases bank cash; transferring cash to an exchange preserves net worth; buying an investment exchanges cash for an asset; a fee reduces net worth; a market price change affects unrealized profit.

**Validation completed and remaining**

- `flutter test --no-pub`: passed the single existing smoke test in `test/widget_test.dart`. It checks the app/login title; it does not test authentication strength or monetary calculations.
- Final `flutter analyze --no-pub`: no errors, one unused-variable warning, and two style infos. It exits with status 1 because issues remain. An earlier run caught temporary undefined identifiers while source edits were underway; those errors were absent in the final run.
- Controlled, in-memory execution of the existing Node middleware confirmed unverified identity acceptance without Firebase credentials even in production mode. No database connection was made.
- Controlled, in-memory execution of the existing Node DCA calculator confirmed that selling two units after buying one is accepted and clamps the quantity to zero. SQL equivalence was inspected statically; the SQL was not executed against a database.
- Not verified: applied production RLS, account-to-account device behavior on a running app, SQL concurrency under load, physical biometric behavior, release APK networking, live backup/restore, dependency vulnerability audit, or external deployment configuration.

Minimum meaningful tests before real use: wrong/expired MFA code rejection; lock on restart/resume; A-to-B account switching; LKR entry/display round-trip; repeated salary save/edit/delete; full liquidation with realized profit retained; asset-changing/backdated transaction edits; oversell/negative/nonfinite inputs; simultaneous writes; API outage with preserved truthful state; more than one page of history; export/restore reconciliation; and direct cross-user API access denied by deployed policies.

Recommended implementation sequence: authentication and account isolation; currency and ledger correctness; truthful reports and recovery/export; then accounts, daily expenses, budgets, and additional investment types.
